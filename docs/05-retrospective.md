# 05 · 复盘（最难问题、学习收获、下一步）

## 最难的三个问题

1. **旧估算未失效导致的"假不可行"**：生成 standard 脚本后，状态里还留着 premium 的旧估算，模型据此判定"无更可行方案"提前放弃。修复：generate_script 换档位时显式将 estimate 置空（依赖失效语义：estimate 依赖 script）。教训——Agent 的状态是有依赖关系的，"改了上游必须作废下游"，否则模型会基于过期观察做出看似合理实则错误的决策。
2. **重复执行与续跑的语义冲突**：幂等复用（已完成→直接复用）和失败续跑（未完成→继续）看似相似，语义相反。最后明确为：按 final_status 分流——completed 复用并注明未重复扣费；incomplete 清空本会话失败计数后从断点继续，且已成功步骤与费用不重复。
3. **环境变量静默覆盖 .env**：真实模型首跑 401，排查发现运行环境预置了另一个 `OPENAI_API_KEY`，而 `load_dotenv()` 默认不覆盖已有变量。修复为 `load_dotenv(override=True)`。教训：配置优先级必须显式声明，否则"配置了却没生效"这类问题极难排查。

## 学习收获

- ReAct 循环的价值不在"会调用工具"，而在**观察驱动的重规划**：降级、兜底、诚实报告缺口，都是"看到估算/失败结果后改主意"的产物；trace 里每步记录 decision_basis 才让这些决策可审计。
- 测试失败注入（FaultInjector）比 mock 整个工具更能暴露分支遗漏（重试/降级/停止三分支就是靠注入才测全的）。
- "失败也是有用输出"：incomplete 状态携带缺口数值与已保留结果，比硬凑一个超支方案更有业务价值。

## 如果继续做（下一步）

1. 真实模型补齐多场景验证（失败分支、超预算分支各跑 2-3 组），统计决策稳定性；
2. estimate_cost 失败后的替代路径（如用价格表直接推算）目前未做；
3. 引入约束求解式规划（预算/工期/档位联合可行域），替代"逐档降级"的单向重规划；
4. 若上生产：工具层加真实 API 适配与超时熔断，trace 接入观测平台。
